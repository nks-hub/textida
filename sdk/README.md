# Textida plugin SDKs for JavaScript, TypeScript and Python

A plugin is a program the editor starts; it talks to the editor in JSON-RPC 2.0, one message per line on standard input and output. These two libraries do the talking so a plugin only registers its commands and calls the document API. They have no dependencies.

| Language | Folder | Needs | Sample plugin |
|---|---|---|---|
| JavaScript, TypeScript | `sdk/js` | Node.js 18 or newer | `samples/plugins/js-hello` |
| Python | `sdk/python/textida_plugin` | Python 3.11 or newer | `samples/plugins/python-sdk-hello` |

Both libraries are copied into the plugin folder (`node_modules/textida-plugin` or `textida_plugin` next to the program), because a plugin is installed from one ZIP. The manifest names the interpreter by its full path (`main.executable`).

## Types

`api.schema.json` is the JSON Schema of the calls the libraries make (`document/info`, `document/readText`, `edit/apply`, `edit/propose`, `ui/notify`, the tasks) and of the handshake. It is made from the types of the C# SDK, so the C# SDK and these libraries cannot disagree. `sdk/js/api.d.ts` (TypeScript) and `sdk/python/textida_plugin/api.py` (TypedDict classes) are written from that schema.

The files are generated by a test; to write them again after a change of the C# types:

```
TEXTIDA_UPDATE_SDK=1 dotnet test tests/NksHub.Textida.Plugin.Tests --filter SdkTypesTests
```

Without the variable the same test fails when a file differs from what the types give.

## Check a plugin

`textida-plugin-validate <folder> --run` checks the manifest, the permissions the plugin declares against the methods it calls, and the handshake of the running plugin. The libraries a plugin carries (`node_modules`, `textida_plugin`) are not searched for the methods it calls; the session of `--run` shows what it really uses. The tests run both samples through the validator with a recorded session (`--scenario`) that writes a selection in capital letters.
